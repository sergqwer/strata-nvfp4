## 零、先说 197 是什么

**197 tok/s 在我们自己的档案里不是实测值，是一条外推。** 原始记录（`strata-nvfp4-fork-0144-single-slot-512k-dynamic-20261019.md` 第 171 行）原文：

> decode ≈ 草稿接受率的线性函数：接受 47% → 121；68% → **197**；75–82%（旧版真实业务）→ 170–181。

同一份档案里**实测的"写 Python 脚本"任务是 177.7 tok/s（接受率 64%，432 token）**。所以 197 是"如果接受率到 68% 会是多少"的推算。

**今天的结论：不用推算，实测就已经超过 197。**
- 社区脚本自带的编程题（写 Python 合并函数）：**283.0 tok/s**（三次 247.6 / 284.0 / 283.0）
- 现场写的完整 Python 脚本（552–608 token，全部编译通过）：**260.1 tok/s**（三次 260.1 / 269.2 / 259.4）
- 我另设的 4 类代码任务 12 次请求：中位 **218.2 tok/s**

## 一、跑的是哪支脚本，为什么是它

官方 `docs/BENCHMARK_PROTOCOL.md` 开头就写明白：

> Today's `BENCH.bat`, `./bench.sh`, and `tools/strata_bench.py` do not implement this protocol. Continue using the community guide for current reports.

也就是说：**那份"标准协议"还只是草稿，社区实际在用的就是 `tools/strata_bench.py`**（社区指南推荐、PR #2954 等社区基准都用它）。所以"社区的同样的测试脚本"= 它。

它的套件（默认 thinking off、温度 0、每个 prompt 带唯一 tag 保证冷读）：

| 阶段 | 内容 | 输出上限 | 请求数 |
|---|---|---|---|
| warm-up | 1 条短问 + 1K prompt，丢弃 | — | 2（不计入） |
| short chat | 3 个短问题 × 3 次 | 100 token | 9 |
| 4K / 16K /（`--long`）32K | 每档 3 个全新 prompt | 24 token | 9 |
| agent 会话 | 系统提示 + 4 个工具，5 轮各追加约 1500 词项目文件，继续模型自己的回答 | 64 token/轮 | 18 |
| 可选并发 | 4 路同发 | 128 | 未跑 |

**关键点：3 个短问题里的第 1 题就是编程题**（"写一个合并两个有序列表的 Python 函数，带 docstring 和两个测试"）。所以这套脚本本身就在测代码任务。

## 五、机制：为什么代码快、解释慢，197 在哪一格

把今天 30 次请求（12 代码 + 15 形态 + 3 补测）的"接受率 → decode"做线性回归：

```
decode(tok/s) ≈ 22.5 + 2.683 × 接受率(%)
```

| 接受率 | 预期 decode | 典型负载 |
|---|---|---|
| 40% | 130 | 中文长文总结、开放式行文 |
| 50% | 157 | 需要推理的代码修复 |
| 60% | 184 | 混合内容 |
| **65%** | **197** | **← 197 对应这一格** |
| 68% | 205 | |
| 79% | 235 | 写 Python 脚本 |
| 88% | 259 | SQL / JSON 结构化输出 |

分桶实测（中位）：30% → 119.1｜40% → 125.1｜50% → 158.9｜60% → 181.3｜70% → 190.5｜80% → 256.4｜90% → 239.8。

**结论**：投机解码（MTP）猜的是"下一步最可能是什么"。代码、SQL、JSON 的下一步几乎唯一 → 猜得中 → 200–284 tok/s；中文散文下一步有无数种写法 → 猜不中 → 110–140 tok/s。**197 不是极限，也不是常态，它是"猜中率约 65%"那一格的换算值。**

## 六、过程事故（如实记录，与数据无关但影响可用性）

跑旧引擎同脚本 A/B 的脚本里，我用 `$!` 记录的是子 shell 的 PID 而不是 python 进程，`kill` 打空 → **旧引擎进程（69.7 GB）残留在 GPU0**。随后 systemd 拉起 0.2.0 时显存不够，`native dense upload: out of memory`，**连续重启 5 次失败**。

- 影响：本机模型约 **5 分钟不可用**（16:40–16:45）。
- 处置：手工 `systemctl stop` → 精确 kill 残留 PID（1259523/1259532/1259525）→ 显存回落到 5 MiB → `systemctl start` → **20 秒恢复**，`NRestarts=0`，引擎 `0.1.45.3`、2 槽、22,106 专家、余量 2,966 MiB。
- 教训（已写进技能）：**这套 server 的引擎是独立子进程，杀父不杀子**；停测试实例必须等 `nvidia-smi` 显存真回落再起下一个，不能用 `$!` 直接 kill。

## 七、未做 / 限制

- 社区套件只跑了**串行单请求**（`--clients` 并发档没跑），因为我们生产是 2 槽，4 路并发会排队，跑出来会被误读成"4 路并行解码"。
- 三个短问题的 decode 波动很大（新旧都如此，区间 155–284），这是内容驱动的，不是抖动；因此只报中位+区间，不报单次。
- 代码题的输出上限 512 会截断（旧记录也是 432 截断），所以 §三 补了 1200 上限的完整版用于验证；**不截断的那版才是 260 tok/s 的可交付口径**。
- A/B 的旧引擎跑的是同一份社区脚本，但两份 README 的机器信息、上下文（都 524288）、槽数（都 2）一致；采集时间相差约 4 分钟，机器温度/功耗未记录。
- 没有做社区标准协议（`BENCHMARK_PROTOCOL.md` 那份草稿）要求的 21 请求套件——官方自己说工具尚未实现它。

## 八、一句话回答你的问题

**197 tok/s 是真的能到，而且今天实测到了更高的：代码任务 250–284 tok/s（中位 256–283），比 197 高 30%–44%。**
但它只在"下一步很确定"的内容上出现——代码、SQL、JSON。你要它写中文长文，它还是 110–140 tok/s，这一点新旧引擎没差别。旧引擎当年其实也能到 245–248（社区脚本的编程题），所以 197 从来不是天花板，只是那份档案里按 68% 接受率换算的一个中间值。
